# SimpleTranslatorCS 架构评估

后续三项目集成规划与接手入口见 [docs 导航](README.md)。本文保留第一次服务端架构检查的证据，后续方案以集成设计和进度文档为准。

检查日期：2026-09-19。结论：不建议彻底重写；建议保留翻译资产和双版本构建，对覆盖引擎进行有边界的重构。

## 检查范围与证据

- 项目：SimpleTranslator.cs、DialogueLocalizer.cs、ItemPlaceholders.cs、Jsonc.cs、ModConfig.cs、TranslationReport.cs、构建配置及测试。
- 本机 4.0 服务端：`V:\EFToffline\EFToffline - 4.0debug\SPT`，Core 实际版本 **4.0.13**，.NET 9。
- 本机 4.1 服务端：`V:\EFToffline\EFToffline - 4.1debug\SPT_Runtime`，Core 实际版本 **4.1.3**，.NET 10。
- 项目编译依赖：NuGet Core **4.0.9 / 4.1.2**，不是上述两台本机服务端的补丁版本。
- 使用本机 ILSpy 检查实际程序集中的 LazyLoad、ImporterUtil、LocaleService、DataCallbacks、OnLoadOrder；另检查 4.1.3 的 GlobalLocaleDictionary、DataDynamicRouter、SptHttpListener、TemplateTable、DatabaseIntegrityService。
- 在临时目录编写隔离验证程序，直接加载这四个版本的实际 Core DLL，验证 LazyLoad 更新和删除覆盖项的行为。4.0 DLL 的隔离程序运行在 .NET 10，不代替 .NET 9 完整服务器集成测试。
- 现有已编译测试运行结果：24/24 通过（`dotnet test --no-build --no-restore`，没有重新编译，不能据此宣称当前源码或完整游戏兼容性已验证）。
- 没有启动或修改游戏服务端，没有做客户端在线刷新和完整 mod 组合测试。本次只新增本评估文档。

## 最关键的发现：不能只按 4.0 / 4.1 二分缓存机制

| 实际检查版本 | Locale 容器行为 | 热更新基础能力 |
| --- | --- | --- |
| 4.0.9、4.0.13 | `LazyLoad<T>.Value` 每次反序列化并按注册顺序执行 transformer；没有 `Clear()` | 单个 transformer 读取最新翻译快照，下次读取即可生效 |
| 4.1.2 | 同样每次读取重新构建；没有缓存构造参数和 `Clear()` | 与上述方式相同 |
| 4.1.3 | `GlobalLocaleDictionary` 标记 `[CacheLazyLoad]`；ImporterUtil 按标记启用缓存；LazyLoad 提供 `Clear()` | 发布新快照后清理目标语言缓存，下次读取重建 |

在 4.1.3 中，`AddTransformer()` 本身也会调用 `Clear()`，但不能把“每次保存都追加 transformer”作为热加载方案：旧闭包不会删除，链会持续增长，删除词条也无法正确撤销旧覆盖。

当前 README 和 SimpleTranslator.cs 的“locale 字典构建后即固化，因此无法真正热重载”判断不成立。当前真正固定的是闭包捕获的启动时 `content`，且文件监听器只打印日志。

官方仓库中的 [LazyLoad 源码](https://raw.githubusercontent.com/sp-tarkov/server-csharp/main/Libraries/SPTarkov.Server.Core/Utils/Json/LazyLoad.cs)也展示了无缓存实现，尽管其注释提到缓存。因此本评估以本机具体版本的实现与实验为准，不把仓库主分支当作所有补丁版的实现。

**适配含义：**项目当前引用 4.1.2，直接在现有编译目标上调用 `Clear()` 会遇到 API 不存在的问题。可保留 4.1.2 编译基线，在适配层对公开 `Clear()` 做一次能力探测并缓存委托；没有该方法时使用无缓存路径。另一选择是把最低支持版本明确提高到 4.1.3。不要通过反射篡改私有缓存或 transformer 列表。

## 当前实现的实际问题

1. **文件覆盖顺序没有显式定义。**普通 locale 的 `Directory.EnumerateFiles`（SimpleTranslator.cs:154）和 dialogue 扫描（430）均没有排序，也没有翻译包优先级。后者覆盖前者，但文件系统枚举顺序不是可靠的业务规则。
2. **“最后加载”的保证过强。**当前 `PostSptModLoader + 1` / `PostLoad + 1`（73、83）只能排在更低优先级之后，不能压过 `+1000`、`int.MaxValue`、同优先级后注册组件或运行时更新。实际 4.1.3 的 PostLoad 为 1000000；4.0.13 的 PostSptModLoader 为 1100000。这些数值不是所有 mod 的终点。
3. **占位符只在单文件内做两遍处理。**每文件一个 transformer（235），先写该文件、再解析（257）。如果 A 的任务目标引用物品名，而 B 才提供最终中文名，A 已经生成的文字不会因 B 更新而重新计算。调整文件排序只能暂时规避，不能解决跨包依赖。
4. **英文参考库是启动时捕获的快照。**`referenceLocales`（140）被闭包持有，不能代表后续其他 mod 的所有新增内容。报告预览又只包含当前文件，跨文件引用可能被误报。
5. **“键存在”不等于“最终生效”。**当前报告（172）主要判断 en/ch 中是否有键；冲突失败方仍可被记为生效。反过来，代码实际允许新增 locale 键；原库没有该键也不能证明客户端不会使用它。需要分别报告“基底存在”“实际写入”“最终胜出”“引用关系未知”。
6. **Dialogue 是一次性原地写入。**DialogueLocalizer.cs:86 没有保存原值及归属，重复 Apply 不能正确撤销删除的译文。若扩展为在线热更新，还需处理 HTTP 序列化与写入并发。4.1.3 的 `/client/dialogue` 以流式方式序列化当前表，给写入方单独加锁不能保护不使用该锁的读取方。
7. **JSONC 正则有文本损坏风险。**Jsonc.cs:15、113 的尾逗号正则不区分字符串内部内容；已复现 `{"text":"hello,}"}` 被改为 `{"text":"hello}"}`。这是应先修复的具体缺陷。建议使用 System.Text.Json 的注释和尾逗号解析选项，保留重复键、类型和编码诊断。
8. **4.1 键比较规则与内部报告不一致。**4.1.2/4.1.3 的 GlobalLocaleDictionary 使用 OrdinalIgnoreCase，而项目内部合并、冲突字典默认大小写敏感；仅大小写不同的键可能在报告中分开、实际写入时互相覆盖。应由适配层提供与目标容器一致的比较器，不能简单把所有键转小写。

另一个注释错误：dialogue 阶段再次调用 GetLocaleDb，并非必然拿不到本 mod 的 transformer 结果。检查的旧实现每次重建，4.1.3 注册 transformer 时会清缓存，所以常规顺序下可以读到已注册的翻译。

## 推荐架构

不需要引入大量框架或立刻拆成多个仓库。先在当前解决方案内形成四个清楚的职责边界：

```text
现有 JSON/JSONC + 可选 manifest + 用户覆盖文件
                     |
        翻译包加载、校验、依赖筛选、确定排序
                     |
       TranslationSnapshot（只读、带修订号和来源）
                     |
        统一覆盖引擎：合并所有键 -> 解析占位符
                     |
         SPT 4.0 / SPT 4.1 适配层
             |                   |
       Global locale          Dialogue
```

- **保留格式兼容。**旧版扁平 JSONC 继续工作，不要求译者迁移。可选 manifest 独立存放在翻译扫描目录以外，避免被现有扫描器当作词条。
- **统一合并。**每个语言注册一个长期存在的 transformer。它在一次执行开始时读取同一个快照；先合并全部有效包，再统一解析引用。不要在 transformer 内递归获取同一语言的 GetLocaleDb，避免递归及锁问题。
- **明确优先级。**推荐内置基础包 < mod 专用包 < 兼容补丁包 < 用户自定义覆盖；同级使用稳定的包 ID 和相对路径排序。报告记录完整覆盖链和最终胜出值。
- **分离适配。**元数据、IOnLoad、表访问、日志、locale 比较器、缓存能力放在版本适配层。JSONC 读取、包筛选、冲突规则和占位符逻辑共享。
- **可扩展范围。**全局 locale、menu locale、dialogue 分别使用受控的数据处理器。当前 Global 覆盖不自动涵盖 Menu 表、客户端硬编码文字、BepInEx 配置标签或已写入存档的邮件正文。

建议的可选 manifest 能力（这是设计建议，当前项目尚不支持）：

- 包 ID、版本、作者、语言、启用状态。
- 适用 SPT 版本范围、目标 mod GUID 和版本范围。
- priority、before/after、requires/conflicts；缺依赖和循环依赖给出明确诊断。
- 覆盖策略：replace、onlyMissing、replaceIfOriginalMatches。
- 精确键及明确键组的启停；翻译包可分别控制“新增键”与“只覆盖已有键”。

目标 mod 应优先通过服务端已加载的元数据识别，文件夹名只能作为兼容回退；语言包的可选目标不应全部声明成主 mod 的强制 ModDependencies，否则用户没装某个可选 mod 就可能无法加载汉化引擎。

## 热加载怎么做，边界在哪里

推荐流程：文件变更 -> 去抖与短暂重试 -> 在后台完整解析候选包 -> 校验与确定合并结果 -> 原子发布快照 -> 按版本使缓存失效 -> 输出修订号和变更统计。

任何文件解析失败时保留上一版有效快照，不能先清空当前翻译再加载。要支持新增、删除、重命名、禁用包，并正确恢复被删除覆盖项的下层值。watcher 的错误/溢出需要重新扫描；关闭时应释放 watcher。重载之间要串行，不能并发修改正在使用的 Dictionary。

这里有三个不同目标：

| 目标 | 本次判断 |
| --- | --- |
| 不重启服务器，下一次 locale 请求拿到新翻译 | 实际 DLL 隔离实验已验证基础机制可行 |
| 正在运行的游戏立即显示新翻译 | 还需客户端主动重新获取语言数据、更新本地缓存和界面，尚未验证 |
| 在线替换 C# DLL 或整个 mod | 与翻译数据热加载不同，不建议作为本次目标 |

4.1.3 的公开 `Clear()` 会重新反序列化基底并重放 transformer。**如果别的 mod 只在启动时直接修改返回的缓存 Dictionary，未注册 transformer，这些修改可能在 Clear 后丢失。**因此不能承诺所有 mod 都兼容。对这类 mod 应提供专门适配或选择不清共享缓存的响应覆盖方式，不能在未知来源变化时盲目恢复旧备份。旧字典引用的持有者也不会因 Clear 自动得到新引用。

即使是 transformer，也可能有外部副作用；设计上要明确重放应幂等，并在真实 mod 组合中检查。第一次清缓存热加载应作为开发模式或可配置功能发布。

Dialogue 建议分阶段处理：先明确保存每个受控文本位置的原值、是否存在、上次写入值和当前归属；恢复时确认该位置仍由本 mod 控制，避免覆盖其他 mod 后续修改。真正并发在线更新更适合在响应阶段生成受控副本并应用快照，不要直接在 FileSystemWatcher 回调里修改共享表。4.1.3 的 TemplateTable.Dialogue 是 init 属性，不能假设普通赋值替换整表就是可用的官方运行时 API。

## 其他覆盖方式比较

| 方式 | 优点 | 代价与适用性 |
| --- | --- | --- |
| 单个原生 transformer + 翻译快照 | 保留 SPT 数据链，服务端 LocaleService 也能读到翻译，跨版本适配较小 | 推荐默认；仍受其他 transformer 的顺序和重放行为影响 |
| Locale / dialogue 响应阶段覆盖 | 更接近最终下发内容，可避免直接改共享表；适合特殊兼容和 dialogue 在线刷新 | 4.0 字符串响应与 4.1.3 StreamedJsonBody 不同；需专门适配，不能假设重复注册路由就会在原路由后执行；仅改 HTTP 响应不会同步服务端内部读者 |
| Harmony 修补读取或回调方法 | 可补缺失的扩展点，容易做定点兼容 | 方法签名与返回类型变化会增加维护量，多 mod patch 顺序仍有冲突；作为明确目标的兼容插件，不宜统管所有翻译 |
| 启动时直接改 GetLocaleDb 返回的 Dictionary | 编码少 | 无缓存版本下不能持久；缓存版遇到 Clear 仍丢失，不宜作为双版本统一策略 |
| 直接修改游戏/SPT 数据库文件 | 表面上简单 | 污染基底、难撤销、更新及其他 mod 覆盖风险高，不推荐 |
| 客户端文本拦截/刷新插件 | 可支持即时预览和服务器 locale 以外的文字 | 与服务端覆盖互补；增加客户端版本维护，不应为普通 locale 全面替代服务端方案 |

因此，更好的办法主要是改善原生覆盖机制的使用方式，而不是换成全局 Harmony 或全量 HTTP 字符串替换。

## 建议实施顺序与验收

1. **先修正确性：**JSONC 解析、稳定排序、全包合并后解析占位符、最终胜出报告；保留现有发布方式。
2. **再提供自由度：**可选 manifest、包启停、版本/依赖筛选、用户覆盖层、覆盖策略；未提供 manifest 的旧文件继续按兼容模式读取。
3. **增加服务端热加载：**单 transformer + 原子快照；无缓存 / 可清缓存按能力分支。先覆盖 Global locale，再完成 Dialogue 的撤销和并发读取方案。
4. **按需求添加客户端预览：**只有要求“保存后当前界面马上变化”时，才引入配套客户端刷新功能。

关键验收场景：跨文件与跨包占位符；冲突优先级；包缺失/版本不符；重命名/删除/禁用；文件保存到一半或语法错误；大小写冲突；并发请求和重载；重载多次但 transformer 数量不增长；4.1.3 其他 mod 直接修改缓存后的兼容行为；4.0/4.1 真正游戏请求与客户端刷新。

隔离实验结果：4.0.9、4.0.13、4.1.2 发布新快照后下一次 Value 读到新值；4.1.3 在 Clear 前读旧值、Clear 后读新值；删除覆盖项后恢复基底值。每文件先解析再由后文件改名的旧值问题、JSONC 字符串误改问题均已复现。这些实验支持架构可行性，不代表端到端热加载已经实现。
